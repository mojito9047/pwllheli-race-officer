# Video recording and live finish camera

The app uses FFmpeg to keep a rolling video buffer. Event clips are then cut from that buffer for starts, finishes and manual horn events.

## What gets recorded

When video recording is enabled and the recorder is healthy:

- Start clip: around the actual start signal for each configured start.
- Finish clip: when the blue **Finish** button is used.
- Manual horn clip: when the app manual horn button or physical manual horn input is used.

The exact pre/post duration can be configured in **Settings → Video Recording**.

## Live finish camera

The **Entries & finish times** tab has a collapsed **Show live finish camera** panel below the boats table. Open it to view the finish camera while using the **Finish** buttons.

The preview is still generated by FFmpeg as a regularly updated JPEG. For USB cameras it uses the same FFmpeg input as recording so the webcam is not opened twice. For RTSP/IP cameras in stream-copy mode, the preview runs as a separate FFmpeg process and can use a lower-resolution sub-stream while the recording process copies only the main stream.

### Live video from the relay

> **Keep the relay's watch page up to date.** The player lives on the relay
> (`deploy/live_stream/site/index.html`), not in the app, so a fix to it only takes effect
> once that file is copied to the relay and Caddy serves it. v0.187 fixes a player that
> could sit paused at 0:00 on a working stream.

If a **live-stream page URL** is configured (Settings → Video Recording → *Public live stream page*), the panel shows the near-live JPEGs while the relay's on-demand stream starts and then **switches to the live stream** — smooth video instead of one frame a second. Closing the panel removes the player again, so the stream only runs while you are watching it.

While the stream is starting the panel says **"Live stream starting — still pictures until it is ready…"**. The player is already loading behind the still picture at that point — it has to be actually rendered, because a browser will not start playing video in a hidden element — and it takes over as soon as it is running (or after about 25 seconds regardless, since a frame that loaded is worth showing whether or not it manages to tell the page it started). The relay only pulls the camera while somebody is watching, so a cold start takes as long as it takes to connect and cut the first video segments; the panel waits (up to two minutes) rather than giving up.

If instead it says **"Live video is not available here — showing still pictures"**, the browser could not load the stream page at all. The usual cause is the relay's `frame-ancestors` policy: it lists who may embed the watch page, and the app running directly on a PC (`http://localhost:5050` — the hut machine's own race sheet, or a test server) is a different origin from `pro.pwllhelisailingclub.org`. The shipped `deploy/live_stream/Caddyfile` lists those local origins; if your relay is running an older config, update it and `systemctl reload caddy`. Competitors reaching the app through `pro.…` are covered by `'self'` and are unaffected.

Two things to keep in mind:

- **The stream is a few seconds behind the water.** It goes hut → relay → Cloudflare → back to you, so it is for watching, not for timing. Take finish times from the horn and confirm them against the **recorded finish clips**, which are cut from the hut's own recording and are frame-accurate.
- **It costs hut bandwidth twice.** The relay pulls the camera from the hut and you then pull the stream back down, so on a metered 4G connection keep the panel closed unless you are using it. The JPEG preview is far cheaper.

## Video source types

### USB webcam

Select **USB webcam** and choose a source from the dropdown. If enumeration fails, use the manual override field with the exact FFmpeg camera name.

Windows DirectShow camera listing command:

```cmd
ffmpeg -list_devices true -f dshow -i dummy
```

Example camera source:

```text
Microsoft® LifeCam HD-3000
```

The app passes this to FFmpeg as a DirectShow video source.

### RTSP stream

Select **RTSP stream** and enter the full RTSP recording/main-stream URL. For the Hikvision camera, the main stream is normally channel `101`, for example:

```text
rtsp://user:password@192.168.1.157:554/Streaming/Channels/101
```

RTSP is often more reliable than USB for a permanently installed finish camera.

#### Recording mode

For IP cameras, especially Hikvision cameras that already encode H.264/H.265, choose **Camera stream copy**. In this mode the app does not re-encode the recording. FFmpeg copies the camera's compressed stream into rolling-buffer segments, then remuxes the selected segments into an MP4 event clip with `-c copy`. File size is then controlled by the camera bitrate rather than by the race-office PC encoder.

Use the camera's own OSD date/time overlay and NTP time sync when using stream-copy mode, because the app cannot burn its own timestamp into the recorded video without re-encoding.

Choose **Re-encode with app timestamp overlay** only when you need the app to burn the PC clock into the picture or when stream copy is not compatible with the source. This is the older path and can make much larger files, especially with the low-latency `ultrafast` encoder preset.

#### Stream-copy buffer format

In stream-copy mode the **Stream-copy buffer format** setting controls the temporary rolling-buffer container:

- **Fragmented MP4 — recommended**: the default from v0.101. This started producing usable segments more reliably with the Hikvision HEVC stream tested at the hut.
- **MPEG-TS — advanced fallback**: kept for cameras that behave better with transport-stream segments, but hut testing showed some Hikvision streams can run without closing usable TS segments.

Both formats still export final start/finish evidence clips as normal `.mp4` files.

#### RTSP timestamp mode

Use **Camera timestamps — recommended** for Hikvision RTSP streams. This follows the camera's RTP timing and is usually smoother than deriving output timestamps from packet arrival time. **Wall clock arrival time** remains available only as a fallback for unusual cameras that send unusable timestamps.

If the video status warns about RTP sequence errors or corrupt frames, the app cannot recreate video that did not arrive from the camera. Lower the camera resolution/bitrate/frame rate, turn off Smart Codec/H.264+/H.265+, use CBR, and use the sub-stream URL for preview.

#### Preview sub-stream

The optional **RTSP preview/sub-stream URL** is used only for the live page preview. For Hikvision cameras this is normally channel `102`, for example:

```text
rtsp://user:password@192.168.1.157:554/Streaming/Channels/102
```

This keeps the live view lightweight while the start/finish evidence clips still use the main stream. If the field is blank, the preview process decodes the main stream for the live JPEG preview. The preview process is independent, so a preview/sub-stream failure should not stop the evidence recorder.

#### Preview JPEG quality

v0.107 adds Settings → Video Recording controls for the still images used by the race-office and optional public preview pages:

- **Preview JPEG size** — `Native preview stream size` preserves the resolution of the configured preview/sub-stream. The 640/960/1280/1920 options scale to that width while preserving aspect ratio.
- **Preview JPEG quality** — FFmpeg JPEG quality where lower is better. `2` or `3` is high quality; larger values create smaller, softer files.
- **Preview frames per second** — normal snapshot refresh rate when keyframe-only mode is off.
- **Preview snapshots from keyframes only** — writes a new JPEG only when the camera sends an I-frame. This gives self-contained, sharp snapshots and normally updates once per second if the camera I-frame interval is set to one second.

For the Hikvision line camera, a good starting point is to set channel `102` to a useful preview resolution such as 1280×720, set **Preview JPEG size** to native, **Preview JPEG quality** to 2 or 3, and set the camera I-frame interval to about one second.

#### Hikvision stream-copy notes

For best stream-copy results, configure the camera for standard H.264 or H.265 rather than H.264+/H.265+ smart codec, use a constant bitrate, and set the I-frame interval to about one second, for example 25 frames at 25 fps. Very low 4K bitrates or smart-codec modes can produce sparse frames that look like periodic freezes because the app is faithfully copying the frames the camera sends.

From v0.100, RTSP stream-copy mode uses two FFmpeg processes:

```text
main stream 101    -> stream copy -> rolling evidence buffer
preview stream 102 -> decode to high-quality JPEG snapshots -> runtime/video/live/latest.jpg
```

This is more robust with Hikvision cameras because opening or losing the preview/sub-stream no longer tears down the main evidence recorder.

v0.99 introduced MPEG-TS stream-copy buffers. v0.101 kept TS available, but made fragmented MP4 the default again because the tested Hikvision HEVC stream produced MP4 segments more reliably. v0.102 changed the RTSP timestamp default back to camera/RTP timestamps after testing showed wall-clock arrival timestamps could contribute to pause/jump artefacts.

## Camera zoom / PTZ presets

For an IP camera that supports Hikvision-style ISAPI PTZ presets, **Settings → Video Recording** can optionally control two presets:

- **Idle / zoomed-out preset** — used when no race is in the start/finish recording window.
- **Race start/finish preset** — used for start and finish recording.

The default switch point is **30 seconds before the first actual start**. Remember that the race form stores the first warning-signal time; the first actual start is warning + 5 minutes. After the race start, the app keeps the race preset active while any entry in that race is still `RACING`, so the camera remains ready for finishes.

The app sends an authenticated `PUT` request to:

```text
/ISAPI/PTZCtrl/channels/<channel>/presets/<preset>/goto
```

For example, with camera URL `http://192.168.1.157`, channel `1` and preset `2`, the app calls:

```text
http://192.168.1.157/ISAPI/PTZCtrl/channels/1/presets/2/goto
```

The preset call prefers the system `curl` implementation, because that matches the manual Hikvision command proven from the hut PC. **Digest** remains the default authentication mode, but Settings also offers **AnyAuth** and **Basic** for cameras whose web-auth setting differs from the original test. Python urllib auth remains as a fallback when curl is not available.

Use **Save and test camera login only** first. It calls the read-only PTZ capabilities endpoint and does not move the camera. Then use **Save and test idle preset** and **Save and test race preset** before relying on automatic switching. A successful manual preset test holds that preset for 30 seconds before the automatic scheduler can switch back to idle/recording mode, so the race officer has time to see whether the camera actually moved. After a test, the Settings page shows the HTTP status, method used, configured auth mode, whether a username/password are saved, the ISAPI URL called, the manual hold-until time and a password-masked equivalent curl command. The camera password field is blank on reload; leave it blank to keep the saved password, or tick **Clear saved camera password** to remove it. The PTZ username/password inputs disable browser autofill because password managers can otherwise insert the Race Officer web-app login rather than the camera login.

## Timestamp overlay

In **Re-encode with app timestamp overlay** mode, recorded video and live preview frames have the race-office PC local time burnt into the top-left corner. Keep the PC clock synchronised by NTP or GPS.

In **Camera stream copy** mode, the recorded clips are not re-encoded, so the app cannot burn in its own timestamp. Use the camera's built-in OSD date/time overlay and make sure the camera is synchronised by NTP. The live preview can still be generated from the stream without affecting the copied recording branch.

## Where files are stored

```text
runtime/video/buffer/          Rolling buffer segments, temporary
data/video_clips/              Event clips to back up
runtime/video/live/latest.jpg  Live preview frame, temporary
runtime/video/ffmpeg_recorder.log
```

The buffer is temporary and lives under `runtime/`. The `data/video_clips/` folder contains the evidence clips that are linked from race results and should be backed up with the rest of `data/`.

## Recorder health

Settings shows:

- Whether FFmpeg is running.
- Latest buffer segment.
- Latest live preview frame time.
- FFmpeg log tail.

If the status says the recorder is running but no buffer segments appear, read the FFmpeg log tail first. Most issues are camera-name, permission, codec or filter errors.

## Public videos

Public competitor pages show video links only after the race is finished. Race-officer pages can show evidence-video links during administration.

For normal hut use, avoid serving the evidence-quality clips directly to crews through the Cloudflare Tunnel because every viewer would use the hut 4G connection. Instead, use **Settings → Video Recording → Public video publishing → Cloudflare R2 public copy**.

When R2 publishing is enabled:

1. The full-quality evidence clip is created locally under `data/video_clips/`.
2. The app creates a smaller H.264 public copy in `data/video_clips/public/`.
3. The public copy is uploaded to the configured Cloudflare R2 bucket using the S3-compatible API.
4. The competitor-facing link redirects to the configured public R2/custom-domain URL once upload is ready.

The full-quality evidence clip is always retained locally even if the public copy fails to transcode or upload. The smaller public copy is the one intended for crew viewing from phones and should be served by R2/Cloudflare rather than by the hut PC.

When public branding is enabled, the public web copy keeps the club logo at the top-left and shows one sponsor logo at a time in the top-right. The sponsor changes every 5 seconds through the uploaded sponsor list. The full-quality local evidence clip is not branded.

Settings required for R2 publishing:

- **R2 account ID or S3 endpoint** — Cloudflare account ID, or the copied endpoint URL such as `https://ACCOUNT_ID.r2.cloudflarestorage.com`.
- **R2 bucket** — bucket that will store the public video files.
- **R2 access key ID / secret access key** — bucket-scoped Object Read & Write credentials. The secret field is blank on reload; leave it blank to keep the saved secret.
- **Public base URL** — the public or custom-domain URL from which viewers will download objects, for example `https://videos.example.com`.
- **Object prefix** — optional folder-style key prefix, for example `race-videos`.
- **Public clip quality** — 720p small or 1080p normal.

Use **Save and test R2 upload** after entering the settings. The test writes `<prefix>/test/race-officer-r2-test.txt`, records the last result on the Settings page, and checks that the generated public URL opens without credentials.

Public-video uploads run one at a time and retry before a clip is marked as failed. If a public page shows **Public video error** but a web copy exists under `data/video_clips/public/`, click **Save and retry failed public video uploads** in **Settings → Video Recording**. The retry reuses the local public copy where possible, or recreates it from the local evidence clip before uploading again.

**On a slow hut connection.** A public race clip is tens of megabytes and the hut is on 4G it shares with a caravan park; from v0.217 an upload is allowed time in proportion to the size of the file rather than a flat ninety seconds — roughly twenty minutes for 20 MB. Underneath that it gives up only if the transfer actually **stalls** (under 8 kB/s for a minute together), so a slow link is left alone while a dead one fails quickly. Two consequences worth knowing on a race evening:

- Uploads are **serial by design** — concurrent transfers on a 4G link fail more often than they succeed — so a slow start video delays the finish clips queued behind it. The last clip of a race can be a long time coming.
- **Public clip quality** is the lever. Dropping 1080p to 720p roughly halves what has to go up, which on a congested link is the difference between a clip arriving while the bar is still full and not.

The full-quality evidence clip never leaves the hut PC, so a failed public upload costs you nothing that matters for a protest.

## Start-line overlay on public videos (experimental)

Optionally, the app can draw the **actual start line** on the public web copies of start and finish videos — from the foreground pole base to the orange ODM buoy (which swings on its anchor). Enable it with **Settings → Video Recording → Draw the start line on public start/finish videos**. It is **off by default**.

- The buoy is detected **once per clip** (a single frame, never per-frame), and the line is burned into the **same encode** that already produces the branded public copy — there is no second pass. The full-quality evidence clip is never modified.
- **Start** videos show the line **red before the start signal and green after it** (the exact start moment inside the clip is known from the segment timestamps). **Finish** videos show it **green** throughout.
- It is best-effort: if the buoy is not confidently found, or Pillow/numpy are not installed, the public copy is published without the line — nothing fails. The outcome (drawn, or why it was skipped, with the detection confidence) is written to the **activity log** (`runtime/logs/activity.log`), so if the line is missing you can see whether detection needs tuning.
- Detection is the same colour-based method used by the live stream. Tune it (buoy swing zone, pole base, line colour/opacity/width) in `data/startline_config.json`; if that file is absent the built-in defaults are used. Because it detects the buoy per clip, no line is drawn if the buoy has been lifted or is hidden.

This needs **Pillow** and **numpy** (added to `requirements.txt`; installed by the standard deployment). It has not yet been proven on real race footage — leave it off until you have confirmed detection against actual recorded clips (grab a frame, tune `data/startline_config.json`).

## Public live image via R2

To reduce live-camera traffic through the hut 4G connection, set **Settings → Video Recording → Public live image** to **Upload latest JPEG to Cloudflare R2**. The app then burns the public branding into the live JPEG locally, uploads one stable object to `<prefix>/live/latest_public.jpg` at the configured interval, and tells the competitor home page to refresh the public R2/custom-domain URL instead of `/public/video/live_frame.jpg`. The live JPEG uses the same sponsor rotation as public videos, selecting the sponsor for the current 5-second slot before the frame is served or uploaded.

This uses the same R2 account, bucket, access key, public base URL and object prefix as public start/finish videos. Use a short but sensible interval such as 5 seconds; every competitor still refreshes the same Cloudflare object, while the hut makes only the configured upload.

Settings shows the latest public live-image R2 status, object key, public URL and frame age at upload. If the option is enabled but the R2 settings are incomplete or no live frame is ready, the status box explains that rather than silently falling back.

Recommended post-race check:

1. Open the race-office race page and confirm the evidence clip link works locally.
2. Check `data/video_clips/public/` contains the smaller public copy.
3. Confirm the object appears in the R2 bucket under the configured prefix.
4. Open the competitor-facing video link in a private browser window and confirm it uses the R2/custom-domain URL, not the hut-PC Cloudflare Tunnel origin.

## Settings layout

The Video Recording settings are grouped into six subsections:

1. **Camera input and recording mode** — source, RTSP/USB details, recording mode, timestamp mode and FFmpeg path.
2. **Live preview and buffer** — preview stream, JPEG settings, keyframe mode and rolling-buffer durations.
3. **Public video and live image publishing** — public clip quality, R2 settings and live-image upload mode.
4. **Camera zoom / PTZ presets** — Hikvision-style preset switching and diagnostics.
5. **Recorder status** — current recorder health, latest segment, live-frame age and log tail.
