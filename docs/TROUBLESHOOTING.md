# Troubleshooting

## Cannot log in

First-run username is `admin`. The password is either the value you set in `RO_INITIAL_ADMIN_PASSWORD` before first launch, or the generated password in `runtime/initial_admin_password.txt` on the race-office PC.

If the password was changed and lost, restore from a database backup or create a controlled reset procedure before operational use.

**Cannot log in when testing locally over `http://`.** Session cookies are marked `Secure` by default, and browsers only store `Secure` cookies over HTTPS — so a login over plain `http://localhost:5050` silently fails to keep you signed in. Start the app with `RO_COOKIE_SECURE=0` for local http testing. In production behind Cloudflare (HTTPS) leave it unset.

**"Too many failed sign-in attempts. Please wait a few minutes and try again."** Repeated wrong passwords for the same user from the same address are rate-limited (8 tries in 15 minutes) to slow brute-force guessing. Wait a few minutes and try again with the correct password, or restart the app to clear the counters immediately.

## Login says "Bad request: CSRF token missing or invalid"

The login page carries a one-time security token that is only valid together with the session cookie set on the same page load. This message means the two did not match — almost always because the login page was opened from a stale cache (a browser's back/forward cache, or a CDN such as Cloudflare caching the HTML) so the visitor received a token with no matching cookie.

The app now marks the login page as non-cacheable and, if the token still fails, sends the user back to a fresh login page rather than showing this error. If a user still hits it:

- Reload the login page (Ctrl+F5 / hard refresh) so a fresh page and cookie are fetched, then sign in again.
- Make sure the browser accepts cookies for the site (private/restricted modes and some enterprise policies block them).
- If the site is behind Cloudflare or another proxy, confirm it is not caching the login/HTML responses — the app sends `Cache-Control: no-store` on the login page for this reason.

## Boat lookup is slow

IRC and YTC rating lists are cached for one hour. The first lookup after startup or after cache expiry may be slower because the app downloads the full source list.

Check:

- Internet access from the race-office PC.
- IRC/YTC URLs in Settings.
- Google Sheet sharing/export permissions for YTC.

## Weather data is not updating

Check:

- Weather station enabled in Settings.
- Station IP/URL is reachable from the PC.
- Polling interval is sensible.
- **Test** button result.
- Whether wind values appear in `get_livedata_info` under `0x0A`, `0x0B`, `0x0C`.

## Wind chart has no history

The background poller must be enabled before the page is opened. Check **Settings → Weather Station** and leave the app running long enough to collect samples.

## Horn does not fire

Check:

- Serial port is correct.
- RTS/DTR selection is correct.
- Output polarity is correct.
- Relay/interface board is powered.
- Settings horn test.
- App logs for serial errors.

Never connect the horn directly to the serial adapter.

## Manual horn input does not log

Check:

- Manual input sensing enabled.
- Horn output is DTR, not RTS, when using the ProLog-style interface.
- RTS is wired to the relay feedback common.
- Relay relaxed / horn off connects RTS to DCD.
- Relay active / horn on connects RTS to CTS.
- Input status on Settings changes from idle to active.
- If Settings shows **Input status unavailable**, sign in again or reload the Settings page so the browser uses the authenticated `/admin/api/hardware/input_status` JSON endpoint.
- Isolation/interface wiring.

Only manual horn events can be assigned as finishes.

## Audio countdown does not speak

Automatic speech is generated on the race-office PC running the app, not in the browser.

Check:

- Audio countdown is enabled in **Settings → Horn settings & Test**.
- Central audio test works on the race-office PC.
- The PC is not muted and the correct output device is selected.
- The PC output is routed to speakers/VHF interface.
- Windows has SAPI/`pyttsx3` available, or the operating-system fallback speech command is available.
- The app log does not show a central audio worker error.

## Final countdown seems out of sync

Central audio is generated by the race-office PC running the app, using pyttsx3/SAPI or an operating-system speech fallback. The horn signal and PC clock remain the authoritative timing references. Use Settings → Horn settings & Test → Start automation and central audio → Save and test central audio before racing, and make sure the hut PC audio output is connected to the VHF/audio interface.

## The activity log has a gap, or stops at a date

Fixed in v0.266, and worth knowing if you are reading logs written before it.
The log used to rotate by **renaming** `activity.log` to
`activity.log.YYYY-MM-DD` at midnight. On Windows that rename fails while any
other process holds the file — most often a restart where the old process has
not quite exited, but a backup or an open editor will do it — and it never
recovered: every line after that retried the same rename and was discarded, with
nothing anywhere saying so.

So **a gap in an old log is not evidence that nothing happened**. It is evidence
that two processes held the file at a midnight. Anything the app did in that
period was done; it was just not recorded.

Each day now goes to its own file named for the day —
`activity-2026-08-17.log` — which is never renamed, so nothing can block it.
Both namings are listed in **Settings → Activity log**, so older files stay
readable. `slow.log` was the same and got the same fix.

## A race recorded no video, and the buffer folder has one old file

The rolling recorder is now **supervised**: a watchdog checks every 30 seconds
and restarts it if the FFmpeg process has died, or if it is alive but has
written no segment for several segment-lengths (an RTSP camera that goes away
without closing the connection leaves FFmpeg sitting there). Before that, the
recorder was only ever started by an app restart, a video settings save, or a
clip being scheduled — so a recorder that stopped overnight stayed stopped, and
the club lost the video for a whole race.

**One stale file is the signature of a stalled recorder, not a dead one.** When
FFmpeg is alive but its camera read has blocked, it holds the segment it was
writing open and never closes it. The buffer trim goes on running and deletes
every closed segment as it ages out — but Windows refuses to delete a file
another process still has open, so that one survives. A folder holding exactly
one segment, timed at the hour things went quiet, means the recorder **stalled**
then, and the clip build afterwards can only report, correctly and uselessly,
that no buffered segments covered the event.

A recorder that has genuinely exited leaves the folder empty instead, because
nothing is holding a file open against the trim.

To find out what stopped it, read the recorder's own log — the watchdog writes
a line there each time it steps in, and FFmpeg writes its exit reason:

```
runtime\video\ffmpeg_recorder.log
```

**Around three in the morning, suspect the camera's own scheduled reboot first.**
Pwllheli's is set to 03:00 on Fridays (camera web page → System → Maintenance). A
reboot is a two-minute outage, and it used to cost the whole day's video because
FFmpeg waited for the camera to come back rather than failing: it is now told to
give up after ten seconds, so the outage costs about a minute and leaves a reason
in the log. Other candidates at that hour are the app's own off-site backup (03:15
by default) and Windows Automatic Maintenance (03:00). **The stale segment's
filename is the evidence** — it is the minute the camera went quiet, so it tells
you which of them to look at. The **Video**
card on the dashboard now carries a *check* flag while the recorder is not
running, and shows how many times it has been restarted since the app started —
a number climbing steadily means something is wrong with the camera rather than
with the app.

## Video recorder says running but no buffer files appear

Open **Settings → Video Recording** and read the FFmpeg log tail.

Common causes:

- Wrong camera name.
- Camera already in use by another app.
- FFmpeg path wrong.
- DirectShow/AVFoundation/V4L2 permission issue.
- RTSP URL inaccessible.
- Timestamp overlay filter error.

On Windows, list camera names with:

```cmd
ffmpeg -list_devices true -f dshow -i dummy
```

Use the exact video camera name or the manual override field.

## A race that had tracks now shows none

Usually because its trackers were deleted on the Trackers page &mdash; the
simulated ones after a demo, say. **Nothing has been lost**: the stored fixes are
kept when a tracker is removed, and each one carries the boat it belonged to.

On **v0.230 and later** the race finds them again by itself and there is nothing
to do. Before that, the app answered "is this boat tracked?" from the trackers
table, so deleting the row made it say no and the chart, the progress list and
the replay all stopped looking. Re-adding the tracker with the **same unique id**
and the same boat restores it on any version.

## The replay stops part-way, or the chart will not run past twelve hours

The replay window is capped at **twelve hours** from the warning signal
(v0.276). The longest race the club has sailed is 2h40, so on a real race you
will never meet this &mdash; if you have, the race almost certainly has a **bad
finish time** or a boat still marked **RACING** from months ago, either of which
makes the app believe the race is still going.

Open the race's **Entries and finish times** tab and look for a finish on the
wrong date, or a boat left on RACING that should be FINISHED, RET or DNC. Fix
that and the replay covers the race again. Nothing has been lost either way:
the fixes are all still stored, and the cap only decides how much of the
timeline one reply carries.

## The replay says some fixes were left out

On a very long race with fast-reporting trackers the reply thins each boat's
track to fit a budget (60,000 fixes across the fleet), keeping the first and
last fix of every boat and spreading the rest evenly. The track is still the
right shape and still starts and ends where the boat did; there are simply
fewer points between. Since the replay runs at six times life, the difference
is not visible.

It is worth a look all the same, because at the club's five-second reporting
interval this should not happen: a 2h40 race is about 1,900 fixes a boat
against a share of 6,600. If a boat is being thinned, check its reporting
interval on the **Trackers** page &mdash; something is reporting far faster than
it was set to.

Before v0.276 there was no cap at all, and a race carrying a mis-typed finish
&mdash; one was stamped 352 days after its gun &mdash; would try to assemble a
year-long replay and could exhaust the hut PC's memory in a single request.

## A boat appears twice in a series result

Two boat records for one boat. A series groups a competitor by boat id, so a
second record is a second competitor: its results sit on their own line and are
scored and discarded separately. A tracker attaches to one record too, so only
one of them is tracked.

Look on the **Boats** page for rows marked *duplicate* &mdash; they share a sail
number once case and spacing are ignored, so `GBR 1210` and `GBR1210` count as
the same. Keep the record that carries the race entries (tick *Include inactive*
to see it: deleting a boat that has raced only deactivates it) and delete the
others, which have no entries and so delete outright.

From **v0.231** this cannot happen again: adding a boat whose sail number is
already on file updates that record instead of creating a rival, so deleting a
boat and adding it back re-links it to its own history.

## No GPS finishes, and the fleet is stuck at the last mark

Two causes worth separating.

- **The mark has dragged, a long way.** Three tests decide a rounding now (the
  radius, the 750 m gate, and closest-approach-and-departure), so a drag has to be
  large to defeat all three &mdash; but the walk is sequential, so when one does,
  every mark behind it stalls. Re-measure it &mdash; *Marks &rarr; Set a position
  from the water*. A correction made **during** the race counts for that race,
  including the boats that had already rounded.
- **The race is set to the wrong finish line.** A race sailed to the ISORA line
  but left on the club line (or the other way round) is being tested against a
  line the boats never cross, so no finish ever fires. Check **Finish line** on
  the Course & start tab.

## GPS tracking: no trackers reporting

Open the **Trackers** page and **Settings → GPS tracking**. Check:

- GPS tracking is **enabled** and the Traccar base URL + API token are set (Settings). The token must have device-management rights for the app to add/remove devices.
- The status says a number are *reporting (a fix within the last hour)* — a red or "never" dot means that tracker has not sent a recent fix. Confirm the tracker is powered, has cellular coverage, and is provisioned to report to the relay's Queclink port.
- **"Could not read Traccar: HTTP Error 403"** — the Traccar base URL is behind Cloudflare and the request is being bot-blocked. The app sends a normal User-Agent to avoid this (v0.167+); make sure the hut app is up to date.
- **"Traccar base URL/API token contains a non-ASCII character"** — a "smart" dash or quote was pasted into the field; re-type it as plain text.
- No boats on the race map: the boat must have a tracker assigned (Trackers page) **and** be entered in the race.

## A tracker I switched on does not appear on the Trackers page

Check in this order:

- **Automatic registration is off.** Without `database.registerUnknown` on the relay, Traccar
  rejects positions from an id it does not know (the tracker gets no error; nothing appears
  anywhere). See `deploy/live_stream/traccar-forward.xml`.
- **It is already set up here.** The list only offers devices the app does not have. Look in
  *Assign trackers to boats* above it.
- **App older than v0.191.** A device Traccar auto-registers belongs to no user, and plain
  `/api/devices` omits those — the same devices Traccar's web UI hides until you switch on
  *All Devices*. Earlier versions never asked for them, so the list stayed empty. v0.191 asks for
  unowned devices and claims one when you adopt it.

## Traccar's web page just shows a spinning circle

Opening the Traccar base URL itself (`https://…/traccar/`) in a browser gives a page that loads and then spins for ever. That path serves Traccar's **REST API**, which the app uses successfully because it adds the `/traccar` prefix to every call. Traccar's own web interface can't work there: it is a single-page app that requests `/assets/index-*.js`, `/styles.css` and `/api/socket` from the **site root**, and the relay sends root paths to the hut app, so the JavaScript never loads. It is not a sign of a broken API or token — check the app's **Settings → GPS tracking** status line instead.

You only need the Traccar UI for Traccar-side admin (users, tokens); adding, assigning and removing trackers is all done on the app's **Trackers** page. When you do need it, reach it on the LAN at `http://<relay-ip>:8082`, over SSH with `ssh -L 8082:localhost:8082 root@<relay>`, or give it its own Cloudflare hostname as described in `deploy/live_stream/README.md` §7 step 6.

## Is Traccar actually pushing fixes, or are we just polling?

Open **Settings → GPS tracking** and read the **Push:** line in the status box:

- *"Push: working — 1,284 fixes received, last just now"* — the forwarder is connected.
- *"Push: configured, but no fix has arrived this way yet"* — the **Push ingest token** here does not match the relay's `forward.header`, or the relay is not forwarding. Nothing else will look wrong: the app carries on polling and every tracker reports, but the automatic horn is a poll interval late.
- *"Push: not configured"* — no token set here; polling only, which is a valid way to run.

The counts are since the app last started, so a restart resets them. The same values are in `/api/track/status` (`ingest_configured`, `forward_count`, `last_forward_age`) if you want to check without opening Settings.

## A boat sails the whole course but is never recorded as finished

The chart shows it crossing, the *Position on the water* list may even read 7/7, but the entry stays
RACING with no finish time. Check in this order:

- **The race is not armed.** GPS finishes are only *recorded* when **Arm GPS auto-finish** is ticked
  on the *Entries & finish times* tab. Without it the tracking engine still works out that the boat
  finished — it simply has no permission to write it down.
- **It is armed, but not auto-confirming.** Armed alone *proposes* the finish for you to confirm;
  only **Auto-confirm (unmanned)** records it without asking. Look for a pending proposal on that tab.
- **The finish was cleared earlier.** Before v0.205, once a GPS finish had been recorded and then
  cleared, the confirmed proposal left behind blocked detection for that boat for the rest of the
  race. Upgrade, or clear the entry's row from `finish_proposals`.
- **It rounded every mark but never crossed the line.** A boat that passes the wrong side of the ODM
  has not finished, and the app is right to say so — check the course chart.

## Boats are not being seen to round a mark

Everything looks right — the boats are on the chart, sailing the course — but the
*Position on the water* list sticks at the same mark for one boat, or for all of
them, and GPS finishes never come.

**Is it one boat, or all of them?** That is the question that splits this, and it
is worth answering before going anywhere in a RIB.

- **All of them, at the same mark** — suspect the mark. Marks drag in storms, and
  the app is then looking for boats rounding a buoy that is no longer there. Since
  v0.258 that takes a large drag rather than a small one: three tests decide a
  rounding and any one is enough, the widest being a gate reaching **750 m** along
  a line through the mark on the hand the course requires. But the walk is
  **sequential**, so a drag big enough to defeat all three stalls every mark behind
  it as well.

  The fix is to go and measure it. On a phone, open **Marks → Set a position from
  the water**, take the boat to the mark, wait for the fix to settle, pick the mark
  and set it. The page needs the club's **https** address; a browser will not give
  a position to a page served over plain http on the local network.

- **Only one boat** — then it is that boat's tracker, not the mark. Check its
  reporting interval and last-fix age on the Trackers page. A tracker reporting
  every few minutes at 6 knots leaves 600 m between fixes, which can step straight
  over a mark: no fix inside the radius, and the straight line between two fixes
  is all the geometry has to work with.

Other things to check, in order:
- **Did the rounding happen before the gun?** Course progress only counts fixes
  after the start signal, and it is sequential, so a mark rounded during the
  pre-start never counts and stalls everything after it.
- **Is the rounding radius sensible?** **Settings → GPS tracking**. Larger is more
  forgiving of a drifted mark but risks counting a boat that merely sailed past.

## GPS finish fired too early / not at all

A boat is only finished once it has rounded every course mark in order and then crossed the line, so a mid-course pass of the ODM does not finish it. If a finish is not detected, check the tracker is reporting frequently enough and that the race was **armed** for GPS auto-finish on the *Entries & finish times* tab. GPS finishes are proposals to confirm against the finish video; the mark-rounding radius is adjustable in Settings.

## Public video will not upload to Cloudflare R2

> `Could not upload public video after 4 attempts: Built-in upload failed: Network
> error: The write operation timed out | curl fallback failed: ... timed out after
> 90 seconds`

**Nothing appears in the bucket at all** when this happens, which is expected
rather than a second fault: an S3 PUT is atomic, so a transfer that is cut off
leaves no object and nothing to resume. Each retry starts again from nothing.

Before v0.217 the two upload paths had flat timeouts — 60 seconds for the app's
own uploader and 90 for the curl fallback. Those are fine on a desk and hopeless
from the hut: a public race clip is tens of megabytes, and the hut is on 4G that
it shares with a caravan park. On a Saturday evening the upload was being cut off
with most of the file already sent.

From v0.217 the allowance is worked out from the size of the file and a floor on
throughput (about 20 kB/s), so a 20 MB clip gets roughly twenty minutes rather
than ninety seconds. Underneath it, curl is told to give up only if the transfer
drops below 8 kB/s **for a minute together** — that separates *slow but working*,
which is left alone, from *dead*, which fails in about a minute instead of
holding the line for the whole allowance.

If it still fails after upgrading:

- **Check the size of the clip.** `runtime/` holds the public copies. Public video
  quality is set in **Settings → Video recording**; dropping 1080p to 720p roughly
  halves the file, and on a link this slow that is the difference between a clip
  arriving before the bar empties and not.
- **Uploads are deliberately serial.** Several finishers close together queue
  behind each other, so a slow start video delays the finish clips behind it. That
  is intentional — concurrent uploads on a 4G link fail more often than they
  succeed — but it does mean the last clip of a race can be a long time coming.
- **A genuinely dead link now fails quickly.** If the message comes back within a
  minute or two rather than after twenty, the problem is the connection or the
  credentials, not the timeout: check the account id, bucket and keys in
  **Settings → Video recording**.
- Evidence video is never affected. The full-quality clip stays on the hut PC
  whatever happens to the public copy; only the public web copy goes to R2.

## A race-office page shows the "hut not available" holding page

That page comes from the **relay**, not the hut, and it is shown when the hut
cannot be reached — *and*, until v0.264, when the hut answered **500**. Those are
not the same thing at all: a 500 means the hut is up and answered, and one
request failed. Saving a new user did exactly that, and an administrator was told
the hut was down.

If a single page or button gives the holding page while everything else works,
suspect an application error rather than the network, and look in the hut's own
log for the traceback. The relay's `Caddyfile` no longer turns a 500 into the
holding page; if yours still lists `500` in `@hut_down`, update it (see
`deploy/live_stream/README.md`).

## The Virtual Race Officer answers "could not reach the hut (504)"

**Almost always the relay, not the hut.** The front door gives the hut a tight
`response_header_timeout` so the holding page appears promptly when the hut is
off — and a Virtual Race Officer command is the one slow thing the hut serves,
because it waits on a language model: **3 to 8 seconds**, against everything else
well under one. A command that ran long was cut off by the relay while the hut
carried on and *completed it*.

That is what a fast 504 means. Cloudflare waits about a hundred seconds before
giving up on a slow origin, so a 504 arriving in five is somebody else's
timeout — and identical commands succeeding then failing is the model landing
either side of it.

Two places to look, in this order:

1. **The relay's `Caddyfile`.** The `/api/assistant/*` block should have
   `response_header_timeout 45s`, comfortably past the app's own 30-second model
   timeout so the *app* is what gives up first and can say why. Reload with
   `sudo systemctl reload caddy`. See `deploy/live_stream/README.md`.
2. **The hut's own slow-request log**, which settles whether the hut was even
   involved:

   ```bash
   findstr assistant runtime\logs\slow.log
   ```

   Lines with a **200** at 3–8 seconds mean the hut answered fine and something
   in front of it gave up. No lines at all for those minutes means the request
   never completed on the hut — then check whether the app was running (it prints
   its version and sizing on every start) and whether cloudflared was up.

**What it means for the command.** Interpreting changes nothing, so a 504 there
carried nothing out. A 504 after pressing **Yes** is genuinely uncertain — the
hut may well have done it, as above — but pressing Yes again is safe: the command
carries a token, a token is carried out once, and a retry either does it or
reports what it already did. The page says so.

## The Virtual Race Officer says "This account does not have permission"

Running racing from the water is a per-user permission and no role grants it,
administrators included. An administrator ticks **VRO** against the
account in *Settings → Users*. The page and both endpoints check it, so the
answer is the same whether it is reached by tapping or by posting.

## The Virtual Race Officer only understands short commands

Look at the grey line under the heading on `/vro`, and at the **Interpreter**
line in *Settings → Virtual Race Officer*. It says which of the two is answering:

- *"not available — no interpreter is configured"*. Nothing typed can be read;
  the page says so and offers no box. An administrator adds a model in
  *Settings → Virtual Race Officer*.
- *"... is configured but its last request failed — HTTP 402: ..."*. The
  provider's own words. A **402** is an empty account, a **400** naming the model
  is an id that does not exist (through Cloudflare it wants the vendor prefix,
  `anthropic/claude-sonnet-5`), a **401** is the key or the header style, and a
  timeout is the hut's uplink. Nothing answers meanwhile — the reply says the
  interpreter did not answer, and gives that reason.

A reply also comes back unusable if the model runs out of room mid-thought —
every reply from this endpoint opens with a thinking block spent from the same
budget, and a long question is a long think. The page says so and suggests a
shorter sentence; `MAX_TOKENS` in `core/assistant_llm.py` is the ceiling, raised
to 4096 after a question about designing a course ran out at 2048.

## A VRO command went to the wrong race

Commands follow the race **the conversation is about** — the last one that
person touched, falling back to the club's current race. A race created for this
evening is not the current race by the clock, so this is usually what you want;
the strip at the top of the page always names the race a command would apply to,
and every read-back names it again.

A race that has **finished** stays the app's current race until another starts.
Commands aimed at it are not refused — correcting a finished race is a real
thing to want — but the read-back says "(which has finished)" and warns you
to say *new race* if that is what you meant.

## Public page does not update quickly

The public page polls for state changes. Check:

- Browser/network connection to the race-office PC.
- The race is part of the current series/current race shown by `/` or `/public/current`.
- The race page was saved after course/start changes.

## Course chart has no nautical background

The route, marks, start/finish line and wind arrow still display without tile background. Tile imagery requires network access to the configured tile URLs or a local tile server.

Check **Settings → Course chart background**.

## Made-up course changed back to a fixed course

This should not happen in current versions. While a made-up course is active, the fixed-course selector is greyed out. Use **Clear made-up course** before selecting a fixed course.

If an older database or version behaves differently, upgrade and re-save the race.


### Black command window left open after Windows login

The automatic Scheduled Task should run hidden. If a black Command Prompt window remains on the desktop after login, the task was probably installed by an older deployment script that started `cmd.exe` directly.

Fix:

```cmd
cd /d C:\RaceOfficer\<your app folder>\deploy\windows
uninstall_startup_task.cmd
install_startup_task.cmd
```

Then log out and back in, or run `restart_startup_task.cmd`.

The manual `start_race_officer.cmd` still opens a visible console window by design. Use it only when diagnosing startup problems.

`python app.py` starts the app with Waitress on port 5050. If the terminal does not show the Waitress startup line, make sure dependencies were installed with `pip install -r requirements.txt`.

## Streams of "Manual horn switch detected" with nobody near the button

The hardware event log fills with `manual-horn-input` events, every few seconds, and each one schedules a start/finish evidence clip. A backlog of those uploads will also hold up the nightly off-site backup, which stands aside while race videos are still uploading.

Cause: **Assert output line during horn blast** was cleared while **manual horn input sensing** was enabled. On the ProLog wiring these are not independent settings:

- DTR drives the horn relay; RTS is held asserted as the relay-feedback common; the relay's auxiliary contact ties RTS to DCD when idle and to CTS when active.
- Clearing the tickbox means active-low, so the app holds DTR *asserted* at idle. That energises the horn relay continuously, and its feedback contact then ties RTS to CTS &mdash; which is exactly the signal the app reads as "the manual button is pressed".

The relay being held in is the more serious half: that is the horn. From v0.242 the tickbox is **locked on** while input sensing is enabled, and the Settings page says why, so the combination cannot be selected. If you genuinely need an active-low horn output for other relay wiring, turn input sensing off first.

To clear a backlog already created: Settings &rarr; Video Recording &rarr; **Give up on stuck public video uploads**. Nothing is deleted &mdash; the evidence clips and any public copies are kept, and Retry can queue them again later.

## The startup log is half unreadable

`runtime\logs
ace_officer.log` reads fine for the timestamped lines and comes out as `R e q u i r e m e n t   a l r e a d y   s a t i s f i e d` for everything pip and the app printed.

Two cmdlets were writing the one file and they do not agree on a default encoding: `Add-Content` for the timestamped lines, `Tee-Object` for the piped output. On some builds of Windows PowerShell 5.1 `Tee-Object` writes UTF-16LE, so half the file was two-byte characters read as one. Windows 11's newer 5.1 build writes UTF-8 from `Tee-Object`, which is why it only showed on the hut.

Fixed in **v0.244**: everything goes through one writer, UTF-8 without a BOM. Existing logs are not converted &mdash; open an older one in an editor that can be told the encoding (Notepad++ &rarr; Encoding &rarr; UCS-2 LE), or just delete it and let the next start write a fresh one.

## Installer shows `NativeCommandError`, and the app never starts

The launcher stops after `Installing/updating Python requirements`, printing a red PowerShell `NativeCommandError` around a *harmless* pip warning, and returns to the prompt without starting the app:

```text
[2026-08-03 12:36:19] Installing/updating Python requirements
cmd.exe : WARNING: Ignoring invalid distribution ~ip (...\.venv\Lib\site-packages)
    + FullyQualifiedErrorId : NativeCommandError
```

Windows PowerShell treats a native command's stderr as an error record, and with `$ErrorActionPreference = 'Stop'` that aborts the script. Any pip warning was enough — the warning itself is not the problem.

**v0.77 attempted this fix and did not succeed.** It routed pip through `cmd.exe` so the streams would be combined, but the `2>&1` was still applied by PowerShell to *cmd.exe's own* stderr, and cmd passes the child's stderr straight through to it, so PowerShell still saw stderr and still raised. The failure stayed latent because the pip step only runs when `requirements.txt` changes. **v0.238 fixes it properly** by judging the step on its exit code alone. Upgrade to v0.238 or later, then reinstall the startup task from `deploy\windows`.

### Clearing the `~ip` warning itself

`~ip` is a leftover folder from pip upgrading itself when it could not delete its old copy (often because a Python process still had it open). It is harmless but pip warns about it on **every** run. To remove it, stop the app and delete the orphans — check first that a real `pip` is still there:

```bat
dir .venv\Lib\site-packages\~ip*
dir .venv\Lib\site-packages\pip*
rmdir /s /q .venv\Lib\site-packages\~ip
rmdir /s /q .venv\Lib\site-packages\~ip-<version>.dist-info
.venv\Scripts\python.exe -m pip --version
```

If the last line reports a version, pip is healthy. If anything went wrong, deleting the whole `.venv` folder and re-running `start_race_officer.cmd` rebuilds it from `requirements.txt`.
